# Vaporwave Vikings Backend Service

The light backend for Vaporwave Vikings, Idle: Express and TypeScript, in-memory storage, guest and platform sign-in, and the single `POST /api/v1/sync` endpoint that validates the batches the game sends. The rules it enforces are in [docs/technical/validation.md](../docs/technical/validation.md); how the game builds batches is in [docs/technical/state-store-spec.md](../docs/technical/state-store-spec.md).

## Scripts

```bash
npm install
npm run dev        # tsx watch, http://localhost:3000
npm run build
npm test           # vitest
npm run typecheck
```

The server reads the game's content tables straight from `../vaporwave-vikings-idle/content` (gear, enemies, biomes, ingredients, courses, economy, `meta.json` for the content version, and `test_vectors.json`). Set `CONTENT_DIR` to point elsewhere.

## API

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/health` | No | Service health check |
| `GET` | `/api/v1/config` | No | Content version, economy and gear tables |
| `POST` | `/api/v1/auth/guest` | No | Create a guest account and session |
| `POST` | `/api/v1/auth/apple` | No | Sign in with Apple |
| `POST` | `/api/v1/auth/google` | No | Google ID token |
| `POST` | `/api/v1/auth/google-play` | No | Play Games server auth code |
| `GET` | `/api/v1/profile` | Bearer | Account and display profile |
| `POST` | `/api/v1/sync` | Bearer | Send queued batches; answers `accepted`, `trimmed`, `rejected` (422) or `conflict` (409) |
| `GET` | `/api/v1/state` | Bearer | The server copy of the player state and its revision |

### Sync in one paragraph

Each request carries `base_rev`, the `content_version`, the `device_id` and the queued batches in order. The server checks revision and order, then that no more seconds were claimed than have passed, then applies each batch to a working copy: gear, unlock and progress changes first (so the gold bound is rated at the batch's own gear), the spend must equal the linear cost of the levels bought, gold earned is capped at `expected_gold_per_second x play_seconds x margin` plus boss and course rewards (over that is `trimmed`, not rejected), and the wallet may not go below zero. The same `request_id` sent twice returns the stored answer. After `rejected` or `conflict` the client fetches `GET /state`.

### Shared maths

`src/content/formulas.ts` mirrors `state/selectors.gd` in the game: gold per metre, coin value, enemy gold, run speed, level cost sums and `expected_gold_per_second`. `content/test_vectors.json`, generated by the game (`godot --headless --path . res://tools/gen_test_vectors.tscn`), pins both sides to the same numbers; the first test block here checks them.

## Notes

- Storage is in-memory and resets when the process restarts, so a game pointed at a restarted server will hit `conflict` and fall back to the server copy flow.
- Guest login works immediately. Apple, Google and Google Play need real credentials in environment variables.
- Away gold, ascension and talent endpoints are not built yet (`formulas.ts` already has the away bands).
- Without vitest's native bindings the tests also run on plain Node 22: `node --experimental-strip-types --test test/api.test.ts` with a small shim that maps `vitest` to `node:test`.
